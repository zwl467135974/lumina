## 这节解决什么问题

本项目的绝大部分代码由 **AI 编写、人类定向**完成。很多人第一反应是"我也在用 AI 写代码，为什么我的项目越写越乱？"

区别不在模型，在**方法**。裸用 AI 做工程会遇到三个致命问题，而本项目沉淀了一套完整的解法——**纲领 + 技能包 + 检查清单 + 自进化**，全部随仓库开源（[AGENTS.md](../../AGENTS.md)、[.agents/skills/](../../.agents/skills/)）。

这一节拆解这套方法论的每一层：它解决什么问题、怎么写、怎么用，以及**如何复制到你自己的团队**。学完你会发现，这套资产比项目代码本身更有 transfer 价值。

---

## 纯 AI 开发的三个真实难题

### 难题一：一致性漂移

AI 没有长期记忆。第 1 天它按 `Controller → Service → ServiceImpl → Mapper` 分层写代码，第 30 天新会话里它可能直接在 Controller 里注入 Mapper——**不是它变笨了，是它忘了**。人脑靠团队规范文档 + Code Review 兜底，AI 靠什么？

### 难题二：规范塞不满上下文

"把规范全部贴给 AI"听起来对，实际不行：全量规范几千行，塞进每次对话，挤占真正的工作上下文，AI 还会在长上下文里"看不到"中间的条目（lost in the middle）。

### 难题三：质量纪律不可靠

即使 AI 知道"写操作要加事务"，它也可能在某个深夜的会话里忘掉。人类的解法是 Code Review——但 AI 的产出量远超人类 review 承受量，**纪律必须在生成前生效，而不是生成后补救**。

## 第一层：AGENTS.md 纲领——AI 的"项目宪法"

[AGENTS.md](../../AGENTS.md) 是 AI 每次会话**自动加载**的纲领文件（155 行），现代 AI 编码工具（ZCode / Claude Code / Cursor 等）都遵循这个约定。

### 结构拆解（对照真实文件）

| 章节 | 内容 | 解决什么 |
|------|------|---------|
| 项目技能包索引 | 13 个技能包的用途、路径、**触发条件** | AI 知道"什么时候该去读什么" |
| 项目结构规范 | 基础包名、模块划分 | 新代码放对位置 |
| 代码规范要点 | 8 条核心规范（各指向技能包详情） | 纲领只放索引，细节在技能包 |
| **后端编码前置检查清单** | 20+ 项交付前检查 | 纪律硬约束 |
| Git 推送/提交规范 | 只推 origin、commit 格式 | 防止误操作 |
| 上下文管理 | 阶段性 checkpoint、新会话承接 | 长项目不断片 |

**设计要点：纲领是索引不是百科**。155 行里没有任何一条规范的完整内容——Redis 怎么用、Flyway 怎么写，都只有一句"见 `lumina_redis` 技能包"。这样既保证 AI 每次都能看到全貌，又不浪费上下文。

### 四镜像同步

```
AGENTS.md ←→ CLAUDE.md ←→ .cursorrules ←→ .github/copilot-instructions.md
```

不同 AI 工具读取不同的约定文件。项目头部注释写明"四份保持同步"——这样**换工具不换纪律**，团队里每个人用自己喜欢的 AI 都遵循同一套规范。

## 第二层：技能包——按需加载的规范库

[`.agents/skills/`](../../.agents/skills/) 下 13 个技能包，2500+ 行规范沉淀：

```
lumina_api_design        lumina_json_serialization
lumina_architecture      lumina_mybatis_plus
lumina_code_style        lumina_observability
lumina_conversation      lumina_redis
lumina_domain_model      lumina_testing
lumina_flyway            lumina_git_commit
lumina_frontend_design
```

### SKILL.md 的标准结构

每个技能包一个目录，里面一个 `SKILL.md`，标准四段：

```markdown
# Lumina Redis 操作规范

## 核心原则            ← 一句话红线（最重要，放最前）
所有 Redis 操作必须通过 RedisCacheManager，
禁止直接注入 RedisTemplate 或 RedissonClient。

## 为什么              ← 讲清动机，AI 才能举一反三
直接用 RedisTemplate 会导致序列化器不兼容、
操作分散、测试困难……

## 支持的操作          ← 可查的干货表
| 方法 | 用途 | 示例 | …

## 正确用法            ← ✅/❌ 对照代码
```

**为什么"核心原则"放最前**：AI 读文件有 primacy 倾向，红线放第一句最不容易被忽略。"为什么"段同样关键——只告诉 AI "必须走 RedisCacheManager" 它会机械遵守，讲清序列化器不兼容的因果后，它遇到新场景也能正确推理。

### 触发条件设计：写什么代码加载什么技能

纲领里每个技能包都标了**触发条件**：

| 你正在做的事 | 自动加载的技能包 |
|---|---|
| 写 Controller / DTO | `lumina_api_design` |
| 写 Mapper / SQL | `lumina_mybatis_plus` + `lumina_flyway` |
| 涉及 Redis | `lumina_redis` |
| 写测试 | `lumina_testing` |
| 提交代码 | `lumina_git_commit` |

这正是 [v3.11 技能系统](../stage-4-ai-agent/)在**开发时**的镜像——运行时给模型渐进披露技能，开发时给编码 AI 按需加载技能，同一理念（**按需加载、精准注入**）的两层落地。

## 第三层：前置检查清单——生成前生效的纪律

纲领里最重要的 20+ 项是这份**后端编码前置检查清单**，摘录几条感受一下：

```
- [ ] 先读已有代码：读一个同类已有模块作为模板
- [ ] 分层完整：Controller → Service → ServiceImpl → Mapper
- [ ] 写操作事务：@Transactional(rollbackFor = Exception.class)
- [ ] 异常用 ErrorCode：throw new BusinessException(ErrorCode.XXX)
- [ ] SQL 列名：INSERT/ALTER 前必须 DESCRIBE 查实际表结构（禁止凭记忆写列名）
- [ ] 调用链完整：改 Service 签名后 grep 所有调用方
- [ ] 数据持久化：新采集的数据必须确认写入 DB
- [ ] 编译验证：mvn compile 通过
```

**每一条都是踩过的坑**。"禁止凭记忆写 SQL 列名"背后是一次真实的迁移失败；"grep 所有调用方"背后是一次构造器签名变更打挂 4 个测试。清单不是拍脑袋写的规程，是**事故驱动的沉淀**——这也是它对 AI 有效的原因：条条对应真实失败模式。

执行时机是"每次新增后端功能"，AI 交付前逐项自查。效果等价于一个不知疲倦的资深工程师做 pre-review。

## 自进化：技能包不是写完就冻结

`lumina_frontend_design` 技能包里有一段特殊指令：

> **自进化**：每次使用后更新 `lumina-frontend/DESIGN.md` 和 `.agents/ui-learnings.md`

也就是说 AI 每次用这套前端规范做完一个界面，要**回写**这次学到的设计经验。`DESIGN.md` 因此沉淀出 187 行持续生长的设计系统。这形成闭环：

```
规范指导实践 → 实践产生新经验 → 回写进规范 → 下次实践更强
```

传统团队的规范文档写完即过时，这套机制的规范**越用越准**。

## 实战纪律：长会话的上下文管理

纯 AI 开发一个 10 万行级项目，还要解决"会话装不下"的问题。纲领里的三条实战纪律：

1. **阶段性 checkpoint**：每完成一个独立任务并提交后，做一个 3 行总结（做了什么/改了哪些文件/下一步），便于上下文压缩后恢复
2. **新会话承接**：大型任务完成后新开会话，保持上下文精简
3. **进度快查**：`git log --oneline -10` 三秒恢复最近工作上下文

配合"每个功能独立提交、commit message 写清动机"，git 历史本身就是 AI 的外部记忆。

## 复制到你自己的团队：五步迁移指南

这套方法**不绑定任何技术栈**，五步迁移：

**第 1 步：写纲领（半天）**。从本项目的 [AGENTS.md](../../AGENTS.md) 改造：保留结构（技能包索引/项目结构/检查清单/Git 规范/上下文管理），替换成你团队的内容。控制在 200 行内——纲领是索引不是百科。

**第 2 步：拆前 3 个技能包（一天）**。别急着拆 13 个，先挑你团队**最容易出错的三个领域**（比如本项目的 Redis、Flyway、API 设计就是重灾区）。每个技能包按"核心原则 → 为什么 → 干货表 → ✅/❌ 对照"四段写。

**第 3 步：定检查清单（持续）**。从今天开始，每个 code review 发现的问题、每次线上事故，都问一句"这条能不能变成清单项"。清单是长出来的，不是写出来的。

**第 4 步：立四镜像**。AGENTS.md / CLAUDE.md / .cursorrules / copilot-instructions 同步一份，头部注释写明同步要求。

**第 5 步：跑一个月再迭代**。观察哪些规范 AI 仍然违反——通常是"为什么"段没讲透，补因果而不是补禁令。

## 常见误区

| 误区 | 正解 |
|------|------|
| 把所有规范塞进 AGENTS.md | 纲领只放索引，细节进技能包按需加载 |
| 只写禁令不写"为什么" | 讲清因果，AI 才能应对规范没覆盖的新场景 |
| 检查清单一次写全 | 事故驱动，每条坑都是真实失败换来的 |
| 规范写完就不管 | 自进化回写，越用越准 |
| 依赖单一 AI 工具的私有配置 | 四镜像同步，换工具不换纪律 |

## 自测题

1. **纯 AI 开发大型项目的三个核心难题是什么？各由哪层资产解决？**
   <details><summary>答案</summary>一致性漂移（纲领：每次会话必加载）、上下文塞不下（技能包：按需加载）、纪律不可靠（检查清单：生成前生效）。</details>

2. **为什么 AGENTS.md 只有 155 行，而规范细节放到技能包里？**
   <details><summary>答案</summary>纲领是索引不是百科：每次会话自动加载的全量内容必须小；细节按触发条件按需加载，既省上下文又避免长上下文中间内容被忽略（lost in the middle）。</details>

3. **技能包里"核心原则"和"为什么"两段为什么缺一不可？**
   <details><summary>答案</summary>核心原则是红线，放最前利用 AI 的 primacy 倾向最不容易被忽略；"为什么"讲清因果，让 AI 在规范没覆盖的新场景也能正确推理，而不是机械遵守。</details>

4. **前置检查清单为什么必须"生成前"执行而不是生成后 review？**
   <details><summary>答案</summary>AI 的产出量远超人类 review 承受量；且清单条目全部来自真实事故（如"禁止凭记忆写 SQL 列名"），在生成前拦截成本远低于事后修复。</details>

5. **"给开发 AI 定制技能包"和 v3.11 的"运行时技能渐进披露"是什么关系？**
   <details><summary>答案</summary>同一理念的两层落地：按需加载、精准注入、规则先行——一个作用于开发时（编码 AI），一个作用于运行时（业务模型）。</details>
