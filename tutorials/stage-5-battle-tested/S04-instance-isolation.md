# S04 — 双实例上线那天，任务表被谁杀了

> **前置要求**：知道"服务可以部署多个实例做负载均衡"这个概念即可
> **预计阅读**：25 分钟
> **难度**：⭐⭐⭐⭐☆
> **对应真实代码**：`AgentTaskStartupReconciler` / `AgentInstanceRegistry`（v3.12.1 修复，[ADR-002](../../docs/zh/design/adr/ADR-002-任务对账实例隔离.md)）

---

## 这节解决什么问题

又一个真实故事。Lumina 的异步任务有个贴心的机制：服务重启后，把卡在"执行中"的任务标记为"已中断"——因为重启后旧的执行线程已经死了，任务永远不会有结果，不标记的话用户会永远盯着一个转圈。

这个机制在单实例上运行了两个版本，完美。然后运维说要上第二个实例做滚动发布。**它瞬间从"贴心机制"变成了"误杀机器"**。

这节课讲：分布式系统里最经典的一类错误——**在多实例环境下，沿用单实例的隐含假设**。以及修复它时的每一个取舍。

---

## 第一层：原来的机制为什么是对的

先给原来的设计说句公道话——它不是蠢，是**在它的世界里完全正确**。

单实例部署，服务重启：

1. 重启前：任务 A 正在执行，状态 `RUNNING`；
2. 重启：执行任务 A 的线程随旧进程消失——**物理上没有任何人会给 A 写结果了**；
3. 重启后：A 停在 `RUNNING`，但永远不会动。用户看到的是永远的"执行中"。

所以启动时跑一个对账器（`ApplicationRunner`）：把所有 `RUNNING` 的任务标记成 `INTERRUPTED`，附一句话——

> "服务重启，任务中断（执行结果未知：仅幂等操作可安全重试）"

这句话本身值得停一下：**"中断"和"失败"是两个词**。失败 = 明确没成功；中断 = **结果未知**，可能成功了一半，可能有副作用。给用户和模型准确的信息（"只有幂等操作可以安全重试"），而不是笼统的"出错了"——这是失败语义学的入门课。

## 第二层：第二台机器上线，鬼出现了

滚动发布流程：先启新实例 B → 健康检查通过 → 摘掉旧实例 A。

B 启动的那一刻，B 的对账器跑了。它看到的"世界"是：数据库里有一批 `RUNNING` 任务。按设定，它把**全部** `RUNNING` 标记成 `INTERRUPTED`。

但那批任务是**A 正在执行的**！A 的线程活得好好的，马上就要写结果了。结果：

```
B 启动 → 对账 → A 的在跑任务全被标记 INTERRUPTED
                                              │
A 的线程跑完 → 写入 COMPLETED + 结果           ▼
                                    用户看到：先"中断"，后"完成"
                                          （状态撕裂，信任崩塌）
```

错误根源一句话：**对账器的隐含假设是"数据库里的 RUNNING 任务都属于已经死掉的那个进程"**——单实例时这个假设永远成立（只有一个进程，它死了就是死了），多实例时它悄悄变成了"所有 RUNNING 任务都属于任何刚启动的进程"，错得离谱。

> 💡 这类 bug 的可怕之处：**代码一行都不用改，部署拓扑一变它就出现**。单测、集成测试全绿——因为测试环境永远是单实例。

## 第三层：修复方案——任务知道自己属于谁

思路很直：任务提交时记下"我是哪个实例提交的"，对账时只处理"**归属实例已经死了**"的任务。三个零件：

**零件 1：任务表加 `instance_id` 列**（V59 迁移）。三个任务创建点（手动提交、定时触发、分治父任务）统一写入。

**零件 2：实例心跳**（`AgentInstanceRegistry`）。每个实例启动时生成唯一 ID，在 Redis 写一个带 TTL 的键（默认 90 秒），每 30 秒续期。TTL 是关键：**实例崩溃（来不及打招呼）时，心跳也会在 90 秒内自然消失**——不需要任何人去"通知死亡"。

```
agent:instance:heartbeat:3f2a9c...  →  "worker-host-1"   TTL=90s
（每 30s 续期；实例死亡后 ≤90s 自动消失）
```

**零件 3：判活式对账**。对账器改成：查出 `RUNNING` 任务涉及的所有实例 → 逐个看心跳 → **只标记心跳不存在的实例的任务**。

B 启动时对账：A 的心跳还在 → A 的任务一个不动。A 后来停机：优雅停机时 A 自己标记自己的任务（`@PreDestroy`）；A 崩溃：心跳 90 秒后消失，任何实例的周期对账（每 5 分钟）兜底回收。

## 第四层：三个值得咂摸的取舍

好的分布式设计不在"做对了什么"，在"每个坏情况你选了牺牲哪边"：

**取舍 1：Redis 挂了怎么判活？——按"活着"处理。**
判活失败时有两种选择：当作死了（激进回收，可能误杀在跑任务）或当作活着（保守，可能延迟回收）。Lumina 选后者，理由：**误杀是不可逆的业务伤害，晚回收只是状态难看一会儿**（周期对账会补上）。宁可漏，不可错。

**取舍 2：存量数据没有 instance_id 怎么办？——默认照旧回收。**
升级时历史 RUNNING 任务的 `instance_id` 是 NULL。默认按"无主"回收（等价旧行为，单实例重启语义正确），但提供了一个开关：**混合版本滚动升级的窗口期**（旧实例不写 ID 也没心跳）可以暂时关掉 NULL 回收——否则新实例会误杀旧实例的任务。这个开关的存在本身就是承认："从旧世界迁到新世界，中间有个尴尬的过渡期。"

**取舍 3：为什么还要周期对账？启动时对账一次不够吗？**
启动对账只在"有实例重启"时触发。如果 A 崩溃后没有任何实例重启，A 的任务要等到天荒地老。周期对账（默认 300 秒）让**任何活着的实例**都能回收死者的任务——把"谁来收尸"从"碰巧重启的那个"变成"任何在岗的"。

## 第五层：怎么发现自己的系统里也有这种假设

三个自查问题，任何"启动时 / 定时批量"逻辑都值得过一遍：

1. **这段代码扫的数据，产权清晰吗？**——"全表扫描 + 批量修改"在多实例下意味着"我在改别人的东西"。谁的数据，谁负责。
2. **它依赖"世界上只有一个我"吗？**——本地缓存、进程内状态、`@PostConstruct` 全量加载……多实例下每个实例都有一份，还会互相不知情。
3. **故障时它选了哪边？**——对每个"不确定"，明确写下选了 fail-fast 还是 fail-safe，以及为什么。没写过的，都是没想过的。

## 面试官会怎么追问

**Q：为什么用心跳而不是实例间直接通信（比如 A 停机时广播）？**
A：广播只覆盖优雅停机，覆盖不了崩溃（kill -9 / OOM / 断电）。心跳 + TTL 的妙处是**用"存在感"代替"告别"**——不依赖死者配合，活着的人靠心跳消失就能推断死亡。这是故障检测的通用套路（Redis 哨兵、K8s 健康探针同理）。

**Q：心跳 TTL 90 秒，意味着最坏情况下任务要多挂 90 秒 + 对账周期，能接受吗？**
A：能。这些任务本来就是死的（执行线程已消失），区别只是"死讯"多久被确认。指标是"状态收敛时间"不是"任务执行时间"——两者的 SLA 完全不同。要缩短就调 TTL 和对账间隔，代价是 Redis 写放大。

**Q：优雅停机时自己标记自己，和心跳消失后别人标记，语义有区别吗？**
A：有，错误信息不同（"服务停机" vs "心跳消失（重启/崩溃）"）——前者用户知道是计划内动作，后者提示可能异常。中断语义里"谁说的、为什么"也是信息。

## 自测题

1. **为什么"启动时全表标记"在单实例是对的，在多实例是错的？一句话说根源。**
   <details><summary>答案</summary>它隐含假设"数据库里 RUNNING 任务的归属进程已经死了"——单实例恒成立；多实例下，刚启动的实例会把别人正在跑的任务当成死者的遗物。</details>

2. **心跳方案为什么能覆盖崩溃场景，而"停机广播"不能？**
   <details><summary>答案</summary>广播需要死者配合（优雅停机才能发）；崩溃进程来不及发。心跳+TTL 反过来——不需要死者做任何事，心跳键自然过期，生者据此推断死亡。</details>

3. **判活在 Redis 异常时返回"活着"，牺牲了什么、保住了什么？**
   <details><summary>答案</summary>牺牲：故障任务的状态收敛时间（要等 Redis 恢复后的下个周期）。保住：绝不误杀在跑任务（误杀=不可逆的业务伤害）。宁漏勿错。</details>

4. **你的项目里还有哪些"单实例假设"？说出排查思路。**
   <details><summary>答案</summary>排查三类：启动时批量数据处理（产权问题）；进程内缓存/状态（每个实例一份且互不知情）；本地文件/内存队列（实例间不共享）。每个问一句"多一个我，这个还成立吗"。</details>
