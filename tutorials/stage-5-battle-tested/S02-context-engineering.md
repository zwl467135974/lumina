## 这节解决什么问题

长对话聊到第 20 轮，会发生什么？教科书答案："上下文超限，报错。"真实工程的答案是一串问题：哪些历史该带？带不下怎么办？压错了信息丢了怎么办？压完了为什么账单没降反升？

这节课把 Lumina 的上下文工程从头到尾走一遍。它的每个设计都在回答一个钱的问题——而最后你会发现，连"摘要格式"都是钱。

---

## 第一步：预算装填——"宁可少带，绝不超窗"

老实现是硬编码"带最近 20 条消息"。问题很明显：20 条短消息可能才 2000 token（浪费），20 条长消息可能 10 万 token（爆炸）。

Lumina 换成**按 token 预算装填**（`TokenEstimator.countWithinBudget`）：

```java
// 文件：lumina-agent-core/.../util/TokenEstimator.java
for (String text : textsNewestFirst) {     // 从最新往最旧装
    int cost = estimateTokens(text);
    if (used + cost > budgetTokens) {
        break;                              // 装不下就停——宁可少带历史
    }
    used += cost;
    count++;
}
```

三个细节，每个都有讲究：

1. **从最新到最旧**——最近的对话信息密度最高，优先保住。
2. **装不下就停（break），不是跳过继续**——如果跳过大消息继续装小的，历史就" perforated"（中间烂了个洞），模型会把不连续的对话当成连续的，产生幻觉。
3. **预算覆盖全部输入**——系统提示 + 长期记忆 + 历史 + 当前输入（图片按 1000 token 记账）一起算，因为 LLM 收费是按**整个请求**收的。

## 第二步：两级压缩——一个免模型，一个保语义

预算装填解决"带多少"，压缩解决"单条太长"。Lumina 分两级，**缺一不可**：

**第一级：确定性修剪（ContextPruner）**——超 4000 字符的消息，保留头尾，中间换成省略标记。不调模型、毫秒级、永远不会"编造"。它丢的是中段的字面细节。

**第二级：LLM 检查点摘要**——让模型把旧历史总结成固定 8 段格式的检查点（关键路径/命令/错误串**逐字保留**），并带"收缩硬保证"：摘要必须比原文短，否则重来。

为什么两级都要？一张表说清：

| | 第一级（确定性修剪） | 第二级（LLM 摘要） |
|---|---|---|
| 速度 | 毫秒 | 一次模型调用（秒级 + 花钱） |
| 信息 | 丢语义（保字面骨架） | 保语义（可能丢细节） |
| 失败模式 | 不会失败 | 模型抽风（所以要收缩硬保证） |
| 角色 | **兜底防线**（模型挂了它也在） | 质量手段 |

> 💡 设计哲学一句话：**能确定性解决的不过模型**。模型是管线里唯一"不可靠还收钱"的组件，把它留给只有它能干的事。

## 第三步：溢出自愈——报错了也别放弃

就算有预算，还是可能超：估算器对代码/JSON 密集内容会**低估**（这类内容 2-3 字符一个 token，不是假设的 4 字符）。怎么办？

Lumina 的做法：LLM 返回"上下文超限"错误后，不等人工干预，**确定性紧急压缩**（保系统提示头 + 最近 2 条 + 中段修剪），然后重试，`max-overflow-retries=1` 限制重试次数。

注意这个设计的立场：**估算器不需要精确，需要的是"偏保守 + 出事有兜底"**。估算误差不是 bug，是被溢出自愈吸收的正常波动——这是系统观，而不是对单个组件的洁癖。

## 第四步：8 段固定格式——摘要为什么还管格式？

这是全篇最值钱的知识点，面试极少有人答得出：**摘要的固定格式，是为了命中 LLM 服务商的 Prompt Cache（KV 缓存）**。

背景：主流 LLM API 有前缀缓存——如果这次请求的开头和上次一模一样，服务商不用重新计算这部分的 KV（注意力里的 Key/Value 矩阵），**价格打折、延迟减半**。而缓存命中的条件是：**前缀逐字节稳定**。

问题来了：滚动摘要每轮都变，放在上下文**前面**会把后面所有内容的缓存全部打碎。Lumina 的对策：

- 摘要是**固定 8 段格式**（结构稳定，同一段落的内容变化不影响其他段落的边界）；
- 摘要整体作为**稳定前缀块**注入，最近对话放后面——最近对话本来每轮都变，放后面正好不连累前面的缓存。

一句话总结这个设计的经济学：**压缩不只省窗口，省的是每次请求的真金白银**。做对这一条，重度用户的成本能差出量级。

## 面试官会怎么追问

**Q：你的 Token 估算误差有多大？误差谁兜底？**
A：CJK 1:1、其他 4:1、图片 1000，是启发式。对代码密集输入系统性低估 → 实际超窗 → 溢出恢复的确定性压缩兜住，重试上限 1 次防成本放大。估算只用于输入侧裁剪决策，**不用于计费**（计费以 provider 返回的 usage 为准）。改进路径（ADR-004）：先观测真实/估算比值，数据证明有必要再做校准系数。

**Q：为什么摘要要"收缩硬保证"？**
A：模型偶尔会"越摘越长"（把总结写成复述）。硬保证（摘要必须小于原文，否则重试/降级到修剪）是防止压缩机制本身失效的保险丝。

**Q：Plan-Execute 路径也要预算吗？**
A：要，占预算的 1/4（历史上下文是子任务规划的背景，不能全占）。同一种机制在不同路径上的**配比**是设计，不是拍脑袋。

## 自测题

1. **预算装填为什么"break"而不是"continue"（跳过装不下的，继续装小的）？**
   <details><summary>答案</summary>continue 会造成历史中间有洞——不连续的对话被模型当作连续的，产生时间线幻觉。break 损失的是最旧的历史，语义伤害最小。</details>

2. **两级压缩各自不可替代在哪？**
   <details><summary>答案</summary>第一级确定性、零成本、永不失败——是模型不可用时的兜底防线；第二级保语义质量——细节理解靠它。只有一级：要么丢语义（L1），要么依赖模型可用（L2）。</details>

3. **KV 前缀对齐省钱的原理是什么？摘要格式和它什么关系？**
   <details><summary>答案</summary>LLM 服务商对请求的稳定前缀有 KV 缓存复用（打折不重算）。命中条件是前缀逐字节一致。滚动摘要每轮都变——固定 8 段格式 + 摘要作为稳定前缀块、易变的新对话放后面，最大化每次请求的可命中前缀长度。</details>

4. **估算器低估导致超窗，为什么说这不是 bug？**
   <details><summary>答案</summary>系统设计里它的误差被显式兜底：溢出恢复（确定性紧急压缩 + 受限重试一次）。估算器的职责是"多数情况下够准"，不是"永远精确"——追求估算器精确的成本（每个 provider 维护 tokenizer）远高于兜底成本。</details>
