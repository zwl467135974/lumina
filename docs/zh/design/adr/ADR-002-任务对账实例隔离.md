# ADR-002：异步任务对账按实例隔离（心跳判活）

- 状态：已采纳（v3.12.1，V59 迁移）
- 关联代码：`AgentInstanceRegistry` / `AgentTaskStartupReconciler` /
  `AgentTaskMapper`（business-agent）

## 背景

v3.11.0 的启动对账把**全库** RUNNING 任务标记 INTERRUPTED——单实例部署语义
正确（重启后旧执行线程必然消失），但多实例滚动发布时，后启动实例的
ApplicationRunner 会把**先启动实例正在执行的任务**标记为中断，产生状态撕裂
（用户看到"中断"，随后又出现结果）。

## 决策

1. V59：`lumina_agent_task` 增加 `instance_id` 列（+ `idx_status_instance`），
   三个任务创建点（手动提交 / 定时触发 / 分治父任务）统一写入；
2. `AgentInstanceRegistry`：实例启动生成唯一 ID，Redis 心跳（默认 TTL 90s、
   TTL/3 续期），停机主动删键；
3. 对账只回收**心跳消失的死亡实例**任务；判活 fail-safe——Redis 异常按存活
   处理（宁可晚回收，不可误杀在跑任务）；
4. 周期对账（默认 300s，首次 ≤60s，可关）：实例崩溃后无需等其他实例重启；
5. 优雅停机 `@PreDestroy` 直接标记本实例任务（不等心跳过期）；
6. 存量 NULL 行默认按无主回收（等价旧行为，单实例升级语义不变）；混合版本
   滚动升级窗口期（旧版实例无心跳）可用
   `lumina.agent.task.reconcile.interrupt-null-instance=false` 暂缓。

## 后果

- 正向：多实例滚动发布不再互杀；崩溃回收不再依赖"有实例恰好重启"。
- 代价：Redis 成为判活依赖（异常时降级为"不回收"，最终一致）；
  心跳 TTL 内崩溃的极端场景由周期对账兜底（最迟约 TTL + 对账间隔）。
- 运维注意：从 v3.12.0 升级到 v3.12.1 时，建议全量停机而非滚动（避免
  NULL 行回收与新实例并存的窗口），或升级窗口期关闭 NULL 回收开关。
