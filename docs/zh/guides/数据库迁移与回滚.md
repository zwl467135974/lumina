# 数据库迁移与回滚策略

> 回答 v3.12 评审缺口 P2-13："迁移不可逆性未文档化"。Flyway 是
> **只进不退**的：已执行的迁移不会自动回滚（无 undo 机制），本文件定义
> 由此产生的纪律与出事后的处置路径。
>
> 配套：迁移编写规范见 `.agents/skills/lumina_flyway/SKILL.md`（写 SQL 前的
> 强制检查），失败记录清理见 `TESTING.md` 常见问题。

## 一、为什么"不能回滚迁移"

- Flyway 以 `flyway_schema_history` 的 checksum 保证已执行迁移不被篡改；
  修改已发布迁移文件会导致后续启动校验失败。
- 业务数据在迁移后立即开始按新结构写入——即使能重建旧表结构，也无法把
  新结构下产生的数据安全地塞回旧结构（列缺失/语义变化）。

**因此回滚单位不是"迁移"，而是"版本"**：应用回退到旧版本 + 数据库保持
新结构（向前兼容），或整库恢复到备份点（接受数据丢失）。

## 二、发布前纪律（让回滚不必发生）

1. **迁移 SQL 对照已验证格式写**（V52 五列格式）——V55、V58 两次同模式
   翻车（INSERT 列数与值数不匹配），单测 mock mapper 抓不住，只有真实
   MySQL 能抓。新增迁移必须在本地真实 MySQL 跑过一次上下文启动。
2. **DESCRIBE 先行**：写 ALTER/INSERT 前先查实际表结构，禁止凭记忆写列名。
3. **备份**：带迁移的版本发布前 `mysqldump` 全量备份（或确认 PITR/binlog
   可用）。没有备份点的迁移发布是裸奔。
4. **兼容性规则**（保证"回应用不回库"可行）：
   - 加列：可空或带 DEFAULT，旧代码 INSERT 不写该列不报错；
   - 加表/加索引：旧代码无感知；
   - 删列/改列类型/改语义：**禁止**与代码同版本发布——必须拆成两个版本
     （先发兼容读写两边的代码，下个版本再删）。

## 三、出事后的处置路径

### 场景 A：迁移执行失败（启动即报 Flyway Error）
按 `TESTING.md`「Flyway 校验失败」流程：清理 `success=0` 记录与半成品
对象 → 修复 SQL → 重启。**没有数据损失风险**（失败发生在事务内或 DDL
前半段，业务还没用新结构写数据）。

### 场景 B：新版本上线后发现缺陷，需要回退应用
优先**回应用、不回库**（依赖第二节的兼容性规则）：
1. 编排平台回滚到上一镜像版本；
2. 数据库保留新结构（加列对旧代码透明）；
3. 新结构下已写入的行，旧代码读到的多列为默认值——确认业务可接受。

### 场景 C：数据损坏 / 无法向前修复
1. 停写入（下线或网关熔断写路径）；
2. 从发布前备份点恢复，或按 binlog 做时间点恢复；
3. 明确宣布备份点之后的数据丢失，评估业务重放方案。

### 场景 D：迁移本身有逻辑错误但已执行（如种子数据写错）
**禁止**修改已执行迁移文件。用**新的前向迁移**修正（V60+ 删错行重插），
这是 Flyway 生态唯一正确姿势。

## 四、多实例发布的迁移协调

- Flyway 默认无分布式锁时多实例并发启动可能重复执行迁移——本项目当前
  单实例部署无此问题；多实例化时启用 `flyway.locks` 或保证"先迁一个实例
  再扩容"的发布顺序。
- 滚动升级窗口期注意 ADR-002 的对账隔离配置
  （`interrupt-null-instance=false`）。

      不含 instance_id，不会引用）

      窗口，见 ADR-002）
