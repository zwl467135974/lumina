# 容量压测指南

> 回答 v3.12 评审缺口 P1-5："无压测/容量数据——SSE 并发连接数、分治批次
> 吞吐、网关 QPS 无一量化"。本指南定义压测口径与脚手架；**数值必须由
> 真实环境产出**，本文不留编造的基线。

## 一、压测口径（测什么、判定什么）

| # | 场景 | 加压对象 | 关注指标 | 判定 |
|---|------|---------|---------|------|
| L1 | 网关/静态 API 吞吐 | 登录、Agent 列表等只读接口 | QPS、p95/p99、错误率 | 错误率 <0.1%，p95 达标线由 SLO-1 反推 |
| L2 | 异步任务提交吞吐 | `POST /agents/{id}/execute`（批量大文本走 batch） | 提交 QPS、队列堆积、Agent 并发限制生效性 | RUNNING 不无限堆积（并发限制收敛） |
| L3 | SSE 并发连接 | `/stream` 长连接保持 + 并发对话 | 并发连接数上限、内存、慢消费者背压 | 连接数达到上限前无 OOM；背压策略不放大内存 |
| L4 | 分治批次 | `POST /{id}/execute/batch`（分片数 10~50） | 监视器轮询延迟（≤2s+余量）、合并正确性 | 千级并发批次下终态延迟有界 |

## 二、压测纪律（防烧钱）

- **必须用最便宜模型或 mock provider**：压测打的是 Lumina 管线，不是
  LLM 钱包。DASHSCOPE 换 1.5-flash 级或本地 ollama mock。
- 压测环境独立数据库/Redis（`lumina_perf`），禁止指向生产或共享开发库。
- 加压阶梯化（如 10 → 50 → 100 → 200 VU），每档稳定 5 分钟再爬档，
  记录的是"从哪一档开始劣化"，不是单点峰值。

## 三、脚手架

`scripts/loadtest/lumina-smoke.js`（k6）。运行：

```bash
# L1 只读吞吐（带真实 JWT）
K6_BASE_URL=http://localhost:8080 K6_TOKEN=<jwt> k6 run scripts/loadtest/lumina-smoke.js

# 自定义阶梯
k6 run -e VUS=100 -e DURATION=5m scripts/loadtest/lumina-smoke.js
```

L3/L4 场景在 L1 稳定后按需扩展（SSE 需要 k6 的 http stream 扩展或独立
WebSocket/EventSource 客户端，脚手架预留 TODO 标注）。

## 四、产出物（压完必须沉淀）

1. 结果表贴回本文件附录：环境规格（CPU/内存/部署模式）、每档 VU 的
   QPS/p95/错误率/资源水位；
2. 把实测 p95 回填 `SLO与告警.md` 的 SLO-3 阈值（当前 60s 是未经压测的
   参考值）；
3. 发现的拐点（如 L3 连接上限）记入 ADR 或部署文档的容量边界。

## 五、与评审清单的关系

- P1-5 的"闭环"定义 = L1~L4 至少一轮真实数据 + SLO 阈值校准；
  本指南与脚手架只是前置件，未经压测前 SLO 文档中的"已知盲区"条目
  保持打开。
