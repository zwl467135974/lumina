# Lumina 全能力最佳实践 — 智能运维平台

> **目标**：用一个「智能运维平台」场景，把 Lumina 的**全部 16 项核心能力**编织成一条连贯的业务流程。所有文件放在 `examples/ops-platform/`，别人 clone 代码 → 配自己的 LLM/RAG API Key → 一键跑通。
>
> **核心原则**：零外部依赖（除 API Key）。缺的工具、MCP server、Webhook 接收端全部自己写最简版；模拟数据全部脚本生成；代码/配置里用环境变量占位，文档说明配自己的 Key。

---

## 一、为什么是运维场景

| 维度 | 运维场景的优势 |
|------|---------------|
| 能力覆盖 | 16 项能力每项都有合理落脚点，不牵强 |
| 数据可控 | 日志/指标可以脚本生成，不依赖真实系统 |
| 业务真实 | 巡检→分析→告警是真实运维痛点，不是为演示而编造 |
| 可验证 | 每步有明确预期结果，易于自动化验证 |

## 二、16 项能力 × 场景映射

| # | 能力 | 在运维场景中的角色 | 触发方式 |
|---|------|-------------------|---------|
| 1 | **Agent 执行（ReAct/Plan-Execute/SSE）** | 巡检 Agent 用 Plan-Execute 模式分析系统状态 | API + Cron |
| 2 | **多模态执行** | 上传系统架构图/监控截图，Agent 视觉分析 | API |
| 3 | **RAG 混合检索** | 查询运维知识库（Nginx SOP / DB SOP / 响应标准） | Agent 内置 |
| 4 | **知识库管理 + 隔离** | 3 个 KB，per-agent 隔离（巡检Agent 只查巡检KB） | 前端/SQL 配置 |
| 5 | **@AgentTool 自定义工具** | ops.readLogs / ops.readMetrics / ops.executeCommand | Java 代码 |
| 6 | **DAG 工作流** | 巡检流水线：采集→分析→严重度判断→报告/告警 | API |
| 7 | **Flowable 工作流** | 等价的 BPMN 标准流程（对比 DAG 引擎） | API |
| 8 | **人工审批节点** | P0 严重故障需人工确认后才升级告警 | 工作流 resume |
| 9 | **Cron 定时触发器** | 每小时自动巡检 | 触发器 |
| 10 | **限流 + 并发控制** | rateLimit=10 防刷 / maxConcurrent=1 防并发冲突 | Agent 配置 |
| 11 | **预算控制** | 限制每日 LLM 调用成本 | Budget 规则 |
| 12 | **Code Interpreter** | Python 生成 CPU/内存趋势图、统计分析 | Agent 工具 |
| 13 | **Webhook 通知（5 渠道）** | 告警推送到自建 Python 接收端（验证 HMAC 签名） | 事件触发 |
| 14 | **MCP 接入** | 自建的文件系统 MCP server，Agent 可读写配置文件 | 配置 + API |
| 15 | **评估框架 + A/B 测试** | A/B 对比两个 Prompt 版本；LLM Judge 评估巡检质量 | API |
| 16 | **OpenAI 兼容端点** | 用 curl/SDK 直接调用巡检 Agent | API Token |

**全程贯穿**：多租户隔离 + 审计日志（@Audit）+ Reflective Memory + 会话管理 + 成本追踪 + Prompt 管理。

## 三、业务流程设计

### 场景叙事

> 某公司运维团队使用 Lumina 搭建智能运维平台。系统每小时自动巡检，发现问题后自动诊断并给出修复建议；P0 严重故障需人工确认后升级告警；所有运维经验沉淀到知识库，Agent 越用越聪明。

## 五、自给自足策略

| 需要的东西 | 外部依赖？ | 我们的方案 |
|-----------|-----------|-----------|
| 运维数据（日志/指标） | ❌ 不依赖真实系统 | `gen_mock_data.py` 脚本生成，3 种模式可切换 |
| 运维工具（读日志/指标） | ❌ 不依赖外部 API | `OpsToolProvider.java` 自己写 3 个 @AgentTool |
| MCP Server | ❌ 不装 npx 包 | `mcp_fileserver.py` ~50 行 Python stdio server |
| Webhook 接收端 | ❌ 不用钉钉/企微 | `webhook_receiver.py` ~60 行纯 Python HTTP 接收端 |
| 多模态测试图 | ❌ 不找图片素材 | `gen_chart.py` 用 matplotlib 生成架构图/趋势图 |
| 运维知识库 | ❌ 不抄外部文档 | 自编 3 篇合理的 SOP 文档 |
| LLM API Key | ✅ 需要用户提供 | 配置文件用 `${LLM_API_KEY}` 占位，文档说明 |
| RAG Embedding Key | ✅ 需要用户提供 | 配置文件用 `${RAG_EMBEDDING_API_KEY}` 占位 |

**环境要求**：Java 21 + Python 3.10+ + MySQL 8 + Redis。仅此而已。

## 七、关键技术约束（已审计确认）

| 约束 | 适配方案 |
|------|---------|
| 触发器只触发 Agent，不触发工作流（`workflowId` 是预留字段） | Cron 触发巡检 Agent；工作流通过 API 手动触发 |
| Webhook 是纯出站（无入站接收端点） | 自己写 Python 接收端，验证 HMAC-SHA256 签名 |
| RAG/Code Interpreter/MCP/Reflective 默认关闭 | 文档说明需要开启的配置开关 |
| Flowable 异步执行器关闭（`setAsyncExecutorActivate(false)`） | 只演示同步 BPMN 流程，不依赖定时器节点 |
| OpenAI 兼容端点用 API Token 认证（sk-xxx，非 JWT） | 文档说明先创建 API Token |
| A/B 变体只能改 LLM 配置/Prompt（不能改 Agent） | 用不同 Prompt 版本做 A/B |

## 八、配置开关汇总

启动 standalone 时需要开启以下环境变量（文档中说明）：

```bash
java -jar lumina-standalone.jar \
  --LLM_API_KEY=<你的LLM密钥> \
  --RAG_ENABLED=true \
  --RAG_EMBEDDING_API_KEY=<你的Embedding密钥> \
  --CODE_INTERPRETER_ENABLED=true \
  --MCP_ENABLED=true \
  --REFLECTIVE_MEMORY_ENABLED=true
```
