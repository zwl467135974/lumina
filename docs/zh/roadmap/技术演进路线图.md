## 第一部分：传统工程层面（深入且高级）

### 1.1 多租户隔离 ⭐⭐⭐⭐⭐

**深入体现在**：

| 能力 | 实现 | 为什么深入 |
|------|------|-----------|
| 自动检测 | `@PostConstruct` 查 `information_schema` 发现含 `tenant_id` 列的表 | 新建表不用维护白名单，自动纳入隔离 |
| SQL 改写 | MyBatis `TenantLineInnerInterceptor` + JSqlParser 自动追加 `WHERE tenant_id = ?` | 业务代码零感知——SELECT/INSERT/UPDATE/DELETE 全自动 |
| fail-closed | 未知表默认隔离（宁可报错不泄露） | 安全优先，防新表遗漏 |
| 向量层下推 | Qdrant payload filter + tenant_id 索引 | v3.4 修复的安全漏洞——向量库不走 MyBatis，手动加 filter |
| 拦截器顺序 | 多租户必须在分页之前注册 | 踩过坑（count 重写报错），注释记录了原因 |

**业界对比**：多数项目要么没有多租户，要么靠手动加 `WHERE`。Lumina 是"业务代码零感知 + 全链路自动隔离 + 防绕过"，这是企业级 SaaS 的硬性要求。

**代码位置**：`TenantLineHandlerImpl.java` / `MybatisPlusTenantConfig.java` / `QdrantRestStore.java`

### 1.2 权限体系 ⭐⭐⭐⭐⭐

**深入体现在**：

```
RBAC 五表模型：user → user_role → role → role_permission → permission
                                                                    ↓
                                                              menu（动态下发）
```

| 能力 | 实现 | 为什么深入 |
|------|------|-----------|
| 声明式权限 | `@RequirePermission("agent:list")` 类/方法级注解 | 一行注解搞定，不用手写 if-else |
| AND/OR 逻辑 | `requireAll=true/false` 控制多权限逻辑关系 | 不是简单的"有就放行"，支持复杂权限组合 |
| 超管绕过 | `SUPER_ADMIN` 角色自动放行 | 系统管理员不用配所有权限 |
| 前端按钮级 | `v-permission` 自定义指令 | 没权限的按钮直接删除 DOM |
| 后端拦截 | `PermissionCheckInterceptor` preHandle 校验 | 前端隐藏只是体验，后端拦截才是安全防线 |
| 动态菜单 | 后端按权限下发菜单树，前端渲染 | 改权限不改前端代码 |
| 双注解兼容 | 同时支持 `common` 和 `base` 两套 `@RequirePermission` | 历史包袱下的兼容设计 |

**业界对比**：不是简单的"登录就能用"，是**前后端双重保障 + 声明式 + 权限驱动菜单 + AND/OR 逻辑**的完整体系。

**代码位置**：`RequirePermission.java`（common+base 两套）/ `PermissionCheckInterceptor.java` / `directives/permission.ts`

---

### 1.3 安全纵深 ⭐⭐⭐⭐☆

**多层防御**：

```
① Gateway/StandaloneFilter：剥离客户端伪造身份头（防 X-User-Id 冒充）
② JWT 校验：签名 + 过期 + Redis 黑名单（登出失效）
③ 多租户拦截：SQL 自动加 tenant_id（防跨租户数据泄露）
④ @RequirePermission：声明式权限校验
⑤ Prompt 注入检测：11 种模式（防恶意指令覆盖 System Prompt）
⑥ PII 脱敏：输出侧手机/身份证/邮箱/银行卡自动打码
⑦ 限流：Per-Agent Redis 滑动窗口
⑧ 文件服务：显式 tenantId 防御检查
```

**为什么高级**：不是单点防护（"加了 JWT 就完了"），而是**从入口到输出的全链路多层防御**。每层独立工作，即使某层被绕过，下一层还能兜底。

**代码位置**：`StandaloneJwtFilter.java` / `PromptInjectionFilter.java` / `OutputSanitizer.java`

### 1.4 容错设计 ⭐⭐⭐⭐☆

**三层容错**：

```java
// 洋葱式装饰器：重试套熔断
Supplier<T> retryable = Retry.decorateSupplier(retry, operation);        // 内层：重试
Supplier<T> resilient = CircuitBreaker.decorateSupplier(circuitBreaker, retryable);  // 外层：熔断
```

| 层 | 作用 | 配置 |
|----|------|------|
| 重试 | 偶发失败自动重试 | 3 次指数退避，只重试可恢复异常 |
| 熔断 | 持续故障快速失败 | 错误率 > 50% 熔断 10 秒 |
| Provider 降级 | 主模型挂了切备用 | priority 优先级排序 |

**为什么高级**：不只是"加了重试"，是**重试+熔断+多 Provider 降级**的三层容错，而且重试"聪明"（只重试网络/超时，不重试参数错误）。

**代码位置**：`LlmResilienceWrapper.java` / `ToolCircuitBreaker.java`

### 1.6 架构设计 ⭐⭐⭐⭐☆

**四层 + 领域模型**：

```
Controller（HTTP 接收）→ Service（业务逻辑）→ Domain（业务规则）→ Infrastructure（DB）
```

| 能力 | 为什么高级 |
|------|-----------|
| Domain 层 | 业务规则内聚在领域对象（`Agent.validateName()`），不是贫血模型 |
| DTO/VO/DO 分离 | 安全（脱敏）+ 解耦（前后端不同步） |
| 统一异常 | ErrorCode 枚举（15 业务域分段）+ BusinessException + GlobalExceptionHandler |
| 统一响应 | `R<T>` 双层错误码（httpStatus + errCode） |
| 依赖方向 | 上层依赖下层，不反向，不跳层 |

**代码位置**：`Agent.java`（Domain）/ `CreateAgentDTO.java` + `AgentVO.java`（DTO/VO）/ `ErrorCode.java`

## 第二部分：AI 能力层面（基础入门偏上）

### 核心判断

AI 的 47 篇教程之所以只能到"基础入门偏上"，**不是教程写得不够好，是代码到哪教程才能到哪**。教程的深度上限 = 项目实现的深度上限。

### 2.1 RAG ⭐⭐⭐☆☆（入门偏上——最接近"深入"的）

**已实现（看起来很完整）**：
- 文档上传 → 分块 → Embedding → Qdrant 存储 ✅
- 混合检索（向量 + 关键词 FULLTEXT）✅
- RRF 融合 + Reranker 精排 ✅
- OCR 5 引擎切换 ✅
- 知识库联邦 + Per-Agent 隔离 ✅
- 向量层租户隔离 ✅

**差距（为什么是"假深入"）**：

| 差距 | 说明 | 业界深入方向 |
|------|------|-------------|
| **单跳检索** | 查一次就拿结果，不管够不够 | Agentic RAG：检索后自评质量，不够就重写查询再查 |
| **无查询重写** | 用户原话直接向量化 | Query Rewriting：把口语化问题改写成更适合检索的表达 |
| **无多跳推理** | 不能"查 A → 发现要查 B → 再查 B" | Multi-hop：复杂问题拆成多步检索 |
| **无自适应深度** | 不管问题简单复杂都查同样多 | Adaptive Retrieval：简单问题浅检索，复杂问题深检索 |
| **分块策略简单** | 固定 500 字 + 重叠 | Semantic Chunking：按语义边界分块 |

**一句话**：检索管线做得很好，但缺少"检索后自评 + 动态重试"的智能层——这是从"检索增强"到"智能检索"的分水岭。

---

### 2.2 Agent ⭐⭐☆☆☆（入门）

**已实现**：
- ReAct 循环（Reason→Act→Observe）✅
- Plan-Execute 三阶段（Plan→Execute→Summarize）✅
- AgentScope SDK 封装 ✅
- Provider Failover ✅

**差距**：

| 差距 | 说明 | 业界深入方向 |
|------|------|-------------|
| **单 Agent** | 一个 Agent 独立工作 | Multi-Agent：swarm/handoff/辩论/角色分工 |
| **预定义工具** | 工具列表写死在配置 | 动态工具发现：Agent 运行时自己找可用工具 |
| **无反思机制** | 执行完就结束，不复盘 | Reflection：执行后自我评估、修正 |
| **无记忆优化** | 记忆只存不整理 | Memory Consolidation：定期整理/压缩/遗忘 |
| **SDK 天花板** | AgentScope 2.0.0 能力有限 | 可能需要更强底座（LangGraph4j/自研） |

### 2.3 工作流 ⭐⭐☆☆☆（入门——"假深入"最明显的）

**已实现**：
- 6 种节点（Agent/Condition/Loop/Parallel/Transform/Human）✅
- Flowable BPMN 引擎 ✅
- 人工审批 PAUSED/恢复 ✅

**差距**：

| 差距 | 说明 | 业界深入方向 |
|------|------|-------------|
| **静态 DAG** | 人提前写好 nodes/edges | Agent 自主生成执行计划 |
| **一次规划** | Plan-Execute 只规划一次 | 动态重规划：执行中发现计划不行就调整 |
| **预定义协作** | 多 Agent 顺序靠 YAML 写死 | Agent 之间自主 handoff、动态分工 |

**一句话**：我们有"工作流引擎"，但没有"智能编排"——所有流程是人设计的，Agent 只是按流程执行的工具人。

### 2.4 其他 AI 维度（均入门级）

## 第三部分：后续技术演进方向

### 按投入产出排序

#### 第一梯队（改动小、价值高、可快速见效）

| 方向 | 改动范围 | 价值 |
|------|----------|------|
| **Agentic RAG** | `DefaultAgentExecutionEngine` 的 RAG 注入逻辑 | 从"查一次"到"查到满意为止"——效果提升最明显 |
| **推理链可观测** | 复用 StreamChunk，加 trace 树渲染 | 调试体验质变，也是卖点 |
| **在线评估闭环** | 评估 + A/B + 线上数据回流 | 形成"评测→优化→上线→再评测"自动循环 |

#### 第二梯队（中等改动、需要架构调整）

| 方向 | 改动范围 | 价值 |
|------|----------|------|
| **真多 Agent 协作** | 基于 MsgHub 或自研 handoff | 从"预定义工作流"到"Agent 自主协作" |
| **知识图谱记忆** | 长期记忆升级为实体+关系图 | 支持关联推理，不只是文本匹配 |
| **自适应 Prompt** | Prompt 从静态模板到动态组合 | 不同场景自动选最佳 Prompt 策略 |

#### 第三梯队（大改动、可能需要换底座）

| 方向 | 改动范围 | 价值 |
|------|----------|------|
| **Agent 自主规划** | 可能需要比 AgentScope 2.0.0 更强的底层 | 从"工具人"到"自主决策" |
| **RLHF/DPO 持续优化** | 需要训练管线 | 需要 ML 能力，非纯应用层 |
| **视频多模态** | 模型+管线 | 需要更强多模态模型支持 |

### 关键决策：AgentScope 是否成为天花板

AgentScope 2.0.0 对于 ReAct/Plan-Execute 够用，但以下场景可能受限：
- 真正的 multi-agent handoff（Agent 之间动态转发任务）
- 复杂状态机（Agent 运行中自主切换模式）
- 流式中间结果的精细控制

**建议**：在启动第二梯队前，先评估 LangGraph4j / Spring AI Agent / 自研执行内核的可行性。这个决策影响后续 1-2 个版本方向。

## 第四部分：诚实总结

### 项目当前的商业价值定位

```
纯 AI 框架（LangChain/LangGraph）
  工程能力弱（无多租户/RBAC/审计）→ 企业不敢用

纯企业框架
  无 AI 能力 → 跟不上时代

Lumina 当前位置
  工程底子扎实 + AI 能力有了但待深化
  → 正好卡在企业落地的痛点上
```

多数企业需要的是"工程可靠 + AI 能用"，而不是"AI 最前沿但工程一团糟"。**当前定位有商业价值**，后续往 AI 深入方向走是增量优化。

### 一句话

> **传统工程层面是"真东西"（面试讲出来有底气），AI 层面是"有框架但缺深度"（后续的主攻方向）。两者不矛盾——扎实的工程底子是 AI 深入的前提，没有可靠的多租户/权限/审计，再强的 AI 也不敢上生产。**
