# Lumina 远期功能规划

> 本文档记录已识别但尚未实现的远期功能，按技术难度排序。
> 最后更新：2026-07-16

## H. OCR / 扫描件 PDF 支持

**难度**: ⭐⭐⭐⭐
**当前状态**: 仅检测到扫描件时给出提示（"当前系统暂不支持 OCR"），无实际 OCR 处理。

### 涉及文件（当前提示位置）
- `lumina-modules/lumina-business-agent/.../mq/DocumentIngestConsumer.java`
- `lumina-modules/lumina-business-agent/.../service/impl/AgentServiceImpl.java`
- `lumina-modules/lumina-business-agent/.../service/impl/KnowledgeServiceImpl.java`

### 实现方案（两个方向）
1. **云 OCR API**（推荐先做）：接入百度 OCR / Google Cloud Vision / 阿里云 OCR，在 PDF 文本提取为空时调用 OCR API 识别页面文字。成本低，效果好，按量付费。
2. **本地 Tesseract**：引入 Tess4J（Tesseract Java 封装），需要安装 native library + 语言包（chi_sim），跨平台部署复杂，适合离线场景。

### 关键决策点
- PDF 逐页渲染为图片需要 PDFBox 或 Apache PDF 渲染库
- OCR 结果的质量直接影响 RAG 入库效果（OCR 错别字会降低检索精度）
- 成本控制：云 OCR 按页收费，需要限制大文件处理

## I. Reflective Memory（自进化记忆）

**难度**: ⭐⭐⭐⭐⭐
**当前状态**: 仅支持固定窗口的会话记忆（Redis 热记忆 + DB 冷存储），无自动整合/反思能力。

### 当前记忆架构
- `MemoryManager`: 双轨记忆（Redis 热记忆缓存最近 N 条 + DB 持久化全部）
- 每次执行加载固定窗口的历史消息，无摘要、无整合

### 实现方案
1. **后台定时整合任务**：定期（如每天凌晨）将旧的会话记忆喂给 LLM 做摘要，提取关键事实/偏好，存为"长期记忆"
2. **LLM 自我反思**：在每轮对话结束后，让 LLM 自行判断是否值得记忆（"用户偏好用中文回复"、"用户是 Java 开发者"）
3. **记忆评分淘汰**：给每条记忆打分（访问频率 + 时间衰减 + 相关性），低分记忆定期清理

### 关键决策点
- 难在效果调优：LLM 提取的"关键事实"可能有幻觉，需要人工审核机制
- prompt 设计：反思 prompt 的质量直接决定记忆质量
- 存储结构：长期记忆需要独立表（entity-attribute-value 或向量存储）
- 隐私：长期记忆可能存储用户敏感信息，需要过期/脱敏机制

## J. Code Interpreter / 沙箱执行

**难度**: ⭐⭐⭐⭐⭐⭐
**当前状态**: 完全未实现。无任何代码执行能力。

### 实现方案（三个方向，按安全隔离强度排序）
1. **Docker 容器隔离**（推荐）：每次执行启动一个临时 Docker 容器（预装 Python/Node），执行用户代码，捕获 stdout/stderr，销毁容器。资源限制通过 Docker cgroups 控制（CPU/内存/网络/超时）。
2. **GraalVM 沙箱**：使用 GraalVM Polyglot API 在 JVM 内执行 Python/JS，通过 ResourceLimits 限制内存和执行时间。无需 Docker，但安全隔离不如容器。
3. **Judge0 / 第三方 API**：调用外部代码执行服务（Judge0、Sphere Engine），完全外包沙箱管理。简单但依赖外部服务。

### 关键决策点
- **安全是第一优先级**：用户代码可能包含恶意操作（文件读写、网络攻击、fork bomb），沙箱必须完全隔离
- Docker 方案需要部署环境支持 Docker-in-Docker 或 sidecar 模式
- 输出流捕获：长时间运行的代码需要流式输出（而非等 30 秒超时后一次性返回）
- 工具注册：Code Interpreter 需要作为 Agent 工具注册（Toolkit），让 LLM 在 ReAct 循环中调用
- 依赖管理：用户代码可能需要 pip install，需要预装常用库或支持运行时安装

### 工作量估算
- Docker 方案：3-5 天（容器生命周期管理 + 工具注册 + 流式输出 + 超时控制）
- GraalVM 方案：2-3 天（但安全隔离较弱）

## K. GraphRAG（图谱增强 RAG）

**难度**: ⭐⭐⭐⭐⭐⭐⭐
**当前状态**: 完全未实现。仅有向量检索 + 关键词检索的混合 RAG。

### 当前 RAG 架构
- `HybridKnowledge`: 并行向量检索（Qdrant）+ 关键词检索（MySQL FULLTEXT），RRF 融合
- `RerankProvider`: 可选重排序（SiliconFlow/Jina/Local/Noop）

### GraphRAG 实现（微软提出的架构）
1. **图数据库引入**：Neo4j（或 Apache AGE for PostgreSQL），存储实体-关系-属性三元组
2. **LLM 实体/关系抽取**：文档入库时，用 LLM 从文本中抽取实体（人名/公司/概念）和关系（A works_at B），构建知识图谱
3. **图查询**：检索时将用户 query 转为 Cypher 查询，找到相关实体的多跳邻居，返回结构化的上下文
4. **图+向量融合**：将图查询结果和向量检索结果做二次融合（图提供结构关系，向量提供语义相似度）

### 关键决策点
- **整条链路都是新技术**：图数据库 + LLM NLP 管线 + Cypher + 图向量融合，每一步都有学习成本
- 实体抽取质量：LLM 抽取的实体可能有噪声，需要 schema 约束 + 人工审核
- 查询构建：自然语言 → Cypher 的转换需要专门的 LLM prompt 工程
- 存储成本：知识图谱需要独立存储，与现有 Qdrant + MySQL 是三套存储
- 适用场景：GraphRAG 适合**关系密集型**领域（法律/医疗/金融），对一般文档库可能过度设计

### 工作量估算
- 最小可用版（Neo4j + 基础实体抽取 + 单跳查询）：1-2 周
- 生产级（schema 设计 + 多跳查询 + 融合策略 + 前端可视化）：3-4 周+

## 优先级建议

| 顺序 | 功能 | 理由 |
|------|------|------|
| 1 | OCR (H) | 用户痛点最直接（扫描件 PDF 无法用），云 OCR API 方案成本最低 |
| 2 | Code Interpreter (J) | Agent 能力的质变（能写代码就能做数据分析/图表/自动化），Docker 方案成熟 |
| 3 | Reflective Memory (I) | 提升长对话体验，但效果依赖调优，可以先做简单版（摘要记忆） |
| 4 | GraphRAG (K) | 最复杂，且只对关系密集型场景有价值，建议有明确业务需求时再做 |
