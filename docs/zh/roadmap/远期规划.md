## ✅ H. OCR / 扫描件 PDF 支持（已完成）

**难度**: ⭐⭐⭐⭐
**状态**: ✅ 已完成（commit `5ec0281` + 审计修复 `52a5167`）

### 已实现内容
- **OcrProvider 接口** + `@ConditionalOnProperty` 模式（与 Reranker 一致）
- **5 个 Provider**: Noop（默认零依赖）/ Baidu / Tencent / Google / Alibaba
- **PdfOcrProcessor**: PDFBox 渲染 → 逐页 OCR → 文本拼接
- **三入口集成**: RAG 异步入库 / RAG 同步入库 / 多模态对话
- **官方签名算法**: 百度 access_token / 腾讯 TC3-HMAC-SHA256 / 阿里 ACS3-HMAC-SHA256 / Google API Key

### 使用方式
```yaml
lumina.rag.reader.ocr:
  enabled: true
  provider: tencent          # none/baidu/tencent/google/alibaba
  api-key: ${OCR_API_KEY}
  secret-key: ${OCR_SECRET}  # 百度/腾讯需要双 Key
```

## J. Code Interpreter / 沙箱执行

**难度**: ⭐⭐⭐⭐⭐⭐
**状态**: 完全未实现。无任何代码执行能力。

### 实现方案（三个方向，按安全隔离强度排序）
1. **Docker 容器隔离**（推荐）：每次执行启动一个临时 Docker 容器（预装 Python/Node），执行用户代码，捕获 stdout/stderr，销毁容器。资源限制通过 Docker cgroups 控制（CPU/内存/网络/超时）。
2. **GraalVM 沙箱**：使用 GraalVM Polyglot API 在 JVM 内执行 Python/JS，通过 ResourceLimits 限制内存和执行时间。无需 Docker，但安全隔离不如容器。
3. **Judge0 / 第三方 API**：调用外部代码执行服务（Judge0、Sphere Engine），完全外包沙箱管理。简单但依赖外部服务。

### 关键决策点
- **安全是第一优先级**：用户代码可能包含恶意操作（文件读写、网络攻击、fork bomb），沙箱必须完全隔离
- Docker 方案需要部署环境支持 Docker-in-Docker 或 sidecar 模式
- 输出流捕获：长时间运行的代码需要流式输出（而非等 30 秒超时后一次性返回）
- 工具注册：Code Interpreter 需要作为 Agent 工具注册（Toolkit），让 LLM 在 ReAct 循环中调用
- 依赖管理：用户代码可能需要 pip install，需要预装常用库或支持运行时安装

### 工作量估算
- Docker 方案：3-5 天（容器生命周期管理 + 工具注册 + 流式输出 + 超时控制）
- GraalVM 方案：2-3 天（但安全隔离较弱）

## K. GraphRAG（图谱增强 RAG）

**难度**: ⭐⭐⭐⭐⭐⭐⭐
**状态**: 完全未实现。仅有向量检索 + 关键词检索的混合 RAG。

### GraphRAG 实现（微软提出的架构）
1. **图数据库引入**：Neo4j（或 Apache AGE for PostgreSQL），存储实体-关系-属性三元组
2. **LLM 实体/关系抽取**：文档入库时，用 LLM 从文本中抽取实体（人名/公司/概念）和关系（A works_at B），构建知识图谱
3. **图查询**：检索时将用户 query 转为 Cypher 查询，找到相关实体的多跳邻居，返回结构化的上下文
4. **图+向量融合**：将图查询结果和向量检索结果做二次融合（图提供结构关系，向量提供语义相似度）

### 关键决策点
- **整条链路都是新技术**：图数据库 + LLM NLP 管线 + Cypher + 图向量融合，每一步都有学习成本
- 实体抽取质量：LLM 抽取的实体可能有噪声，需要 schema 约束 + 人工审核
- 适用场景：GraphRAG 适合**关系密集型**领域（法律/医疗/金融），对一般文档库可能过度设计

### 工作量估算
- 最小可用版（Neo4j + 基础实体抽取 + 单跳查询）：1-2 周
- 生产级（schema 设计 + 多跳查询 + 融合策略 + 前端可视化）：3-4 周+
