# Lumina v3.13.0 路线图 — 上游双源借鉴：只读分级、输入侧外存与执行可视化

> **核心目标：** 延续"机制移植、架构不搬"原则，将 DeepSeek Harness（DSH）与 ZCode 两个上游开源项目的成熟机制合并消化：**把工具审批从"逐次人工确认"升级为"只读自动放行 + 会话级模式"，把上下文外存从输出侧扩展到输入侧，把工作流执行从"日志流"升级为"可审批的计划投影 + 实时面板"**。全部改动不引入新架构层次，落在既有 ToolSecurityPipeline / spill / AgentTurnEvent / 自主编排节点之上。

---

## 一、背景与上游基线

| 上游 | 参考版本 | 借鉴定位 |
|---|---|---|
| DeepSeek Harness（deepseek-ai/deepseek-harness） | 0.1.6-alpha.2 | v3.11 已落地 A1–A6（token 预算、两级压缩、SSE 中断闭合、审批管线、结果 spill、真取消）；本版本消化其剩余候选（phase 钩子、playwright-mcp、image-offload） |
| ZCode（zai-org/ZCode） | 3.14.0（开源仓库，已核验与线上版同源） | 补 DSH 未覆盖的三块增量：命令级只读证明（bash-readonly-policy 20+ 文件的 argv 分层方法论）、输入侧上下文外存（read-file-state 水合）、产品化面板与审批投影（phase graph + artifact dashboard） |

**双验证收敛项**（两个上游独立实现同一机制，风险最低）：`phase(title)` 进度钩子、Playwright 浏览器自动化、历史图片卸载。

### 批次 2 —— 只读分级与会话模式（安全层核心）

|---|---|---|---|---|
| 2.1 | **工具只读分级与自动放行** ✅ 已落地 | ZCode（方法论） | 三层落地：① MCP 工具注解（`readOnlyHint`）映射自动放行；② `code.execute` 只读启发式（语言关键字/导入静态分析，弱判定 fail-closed 走审批）；③ 预留 `util.shell` 设计位——若未来引入 Shell 工具，按 ZCode argv 分层方法论（命令注册表→flag 语义→git 子命令分级）从第一天带上只读策略 | ✅ 名单（精确/前缀通配）+ MCP 注解 + code.execute 启发式三层；管线豁免只降级 ASK；ToolGuard 单调性测试全绿；开关默认关 |

| 2.3 | **文件状态水合（输入侧外存）** ✅ 已落地（Lumina 化收窄） | ZCode（read-file-state） | 实施时按 Lumina 实际收窄：记忆为纯文本（无独立工具输入历史），输入侧真实痛点是大消息逐轮回放。落地为 `HistorySpiller`：超阈值历史 user/assistant 消息全文存 A5 存档表（复用租户隔离），记忆留 head/tail 预览 + artifactId，`util.getArtifact` 按需水合；存档失败保留原文（宁可贵不失真，与工具结果 spill 的硬截断降级刻意不同） | ✅ 大消息不再逐轮常驻上下文（预览远小于原文有单测）；水合走既有 util.getArtifact（防回环机制不变）；agent-core / business-agent 全量回归绿 |

### 批次 3 —— Hook 契约与执行可视化（平台层）

| # | 条目 | 来源 | 落点与方案 | 验收标准 |
|---|---|---|---|---|
| 3.1 | **决策型生命周期 Hook** ✅ 已落地 | ZCode × DSH B1 收口 | 实施为独立决策端口 `AgentLifecycleHook`（六决策点：SessionStart/UserPromptSubmit/PreToolUse/PostToolUse/PostToolUseFailure/Stop）+ `AgentHookInvoker`（组合/隔离/限额），而非扩展观测事件总线——事件是单向通知，决策需要同步返回。标准决策词汇 allow/deny/replace-input/add-context/continue；PreToolUse 在安全管线之前；Stop 续跑同步/流式双路径（流式为递归 defer 段循环）；超时/异常中立放行不崩回合，输出上限截断，continue 防循环上限（默认 3）。开关 `lumina.agent.hooks.enabled` 默认关闭。见《生命周期 Hook 接入指南》 | ✅ 企业合规门实现接口即介入不改引擎（27 用例：组合语义/隔离/限额/接线）；阻断路径带钩子名+理由审计与 403 错误码；agent-core 470 / business-agent 353 全绿 |

## 三、明确不做（合并双上游的排除清单）

- **Computer Use / SSH 远控**（两家均有，均排除）：敏感面大、企业服务端场景弱相关。
- **客户端三端形态 / SEA 打包 / 原生搜索二进制分发**（ZCode）：Lumina 是服务端平台，问题域不存在。
- **插件市场商业闭环**（ZCode）/ **Agent Teams**（DSH）：产品方向不匹配。
- **静态分析深水区**（ZCode taint 分析器）/ **wire 协议扩展**（DSH，需服务端配合）：取思想不搬实现，C-1 抽象已验证方向。
- **Bash 全量命令注册表**：取 ZCode 分层方法论，维护企业精选集即可。

## 四、风险与约束

1. **默认开关原则**：2.1/2.2/3.1/4.1 全部默认关闭或灰度发布（延续 A4 上线时的开关惯例），租户级可控。
2. **模型调用成本**：4.1 记忆整理产生后台模型费用，必须有计量与上限设计后才可启用。
3. **fail-closed 不动摇**：所有新判定路径判不定即走人工审批，拒绝不可翻转（ToolGuard 语义不动）。
4. **验证范围**：agent-core 与 business-agent 全量单测；涉及 base 模块时按惯例补跑 `mvn test -pl lumina-modules/lumina-business-base`；前端批次（1.1/3.3）需 E2E 截图核验。
5. **机制来源标注**：文档与 README 对比表注明借鉴来源（DSH / ZCode / 双验证），与既有 A1–A6 标注惯例一致。
